* bind-mounts: share host directories with smolvm guests
** Overview
bind-mounts is one Ansible playbook, driven by a single configuration file,
that shares host directories with
[[https://github.com/smol-machines/smolvm/][smolvm]] guests.
** Details
One default run validates the configuration, attaches the configured
host directories to each machine, bind-mounts them at their target
paths inside each guest, installs a login hook that re-applies the
mounts, verifies every mount, and records what it observed in a
provenance ledger.

The playbook manages any number of machines and users from the same
file, is safe to re-run in any state reachable through normal playbook
operation, and never touches a mount or volume it cannot prove it
created. Unusual states are refused, not auto-fixed: a mount whose
content does not match the configuration, a volume at a target the
configuration names whose ownership the ledger cannot prove, stack
layers whose ownership the ledger cannot prove, or a machine state the
playbook cannot reason about (it knows only running and stopped), halt
the run with instructions instead of being modified.

Two modes are supported. In bind mode the playbook consolidates every
configured directory under one share directory (share_root), attaches that
share to each machine as a single volume, and inside the guest bind-mounts
each entry from the share to its real target path, so one volume slot serves
any number of directories. In direct mode every configured directory becomes
its own smolvm volume, which is simpler inside the guest but uses one volume
slot per directory. Switching modes is a one-line configuration change:
stop the machines, change the mode, and run the playbook once; it converges
the volume set, restarts the machines, and verifies the result.

The mode choice exists because of a smolvm constraint: a directory attached
directly is its own virtiofs device, and libkrun (the VMM underneath) caps
x86_64 machines at 11 virtio-mmio IRQs, one per device. Balloon, rng,
console, and two block devices take five; the root filesystem, the volume
mounts, and the vsock agent channel share the rest, so a directly created
machine fits at most 4 host volumes (3 for machines created from a packed
.smolmachine archive), and one fewer when anything else adds a device, such
as published ports. The ceiling lives in libkrun, and smolvm has no preflight
for it; see smolvm issue
[[https://github.com/smol-machines/smolvm/issues/941][#941]].
bind mode makes the ceiling irrelevant to the number of shared directories;
direct mode is subject to it.
** Quick start
*** 1 Copy vars.yml.example to vars.yml next to the playbook
The playbook looks for vars.yml in its own directory, next to
bind-mounts.yml; put it exactly there.
#+BEGIN_SRC
cp playbooks/bind-mounts/vars.yml.example playbooks/bind-mounts/vars.yml
#+END_SRC

Edit vars.yml with your machine names, users, and directories. vars.yml is
git-ignored and must never be committed; every path in vars.yml.example is
fictitious.
*** 2 Run the default playbook
#+BEGIN_SRC
ansible-playbook playbooks/bind-mounts/bind-mounts.yml -i inventory -K
#+END_SRC

-K prompts once for the sudo password, because host sudo has no passwordless
rule. The default run validates the configuration, bind-mounts the sources
into share_root, attaches missing volumes to stopped machines, starts each
machine if it is stopped, installs the login hook, applies the guest-side
bind mounts, and verifies the result. The guest may be running or stopped; a
stopped machine is started automatically, so nothing needs to be stopped or
started by hand first. A running machine that needs a volume change halts
the run with a boxed ACTION REQUIRED message naming the machine and the
command to run; stop it and re-run.
*** 3 Log in and use the machines
Log in as usual with smolvm machine exec. The mounts are already in place,
and the installed .bash_profile hook re-applies them non-interactively at
every login as a fallback.
** How to
*** Add a volume
Add a mount entry under the machine in vars.yml and run the default
playbook. Whether the guest can stay running depends on the mode. After a
host reboot, run the playbook before starting a machine: a standalone
start mounts nothing, because the guest scripts refuse to bind from empty
share directories.
**** Bind mode: the guest can stay running
The new directory rides inside the existing share volume, so the run
creates the share subdirectory, bind-mounts it on the host, creates the
target directory in the guest, and binds it from the share, all while
the machine runs.
**** Direct mode: the guest must be stopped
The new mount becomes a new volume, and volume changes require a stopped
machine. A stopped machine is converged during the run; a running machine
halts the run with an ACTION REQUIRED message, so stop it and re-run.
*** Remove a volume
Delete the mount entry from vars.yml and run the default playbook. Guest
target directories are never removed and no data is deleted in either
mode. Whether the guest can stay running depends on the mode.
**** Bind mode: the guest can stay running
The run unmounts everything the ledger proves it created: the host-side
bind, the emptied share subdirectory, and the guest-side bind, except a
target that carries a volume, which the guest side never unmounts.
**** Direct mode: the guest must be stopped; the volume itself is removed
*** Manage a subset of machines
Every run accepts -e limit_machines=name1[,name2...] to scope it to the
named machines only: stop, start, attach, teardown, and the default run
all respect it. Unknown names fail the run. Machines outside the scope
are untouched, and their ledger entries are carried forward unchanged.
*** Change a volume
Changing the target path, the share name, the source directory, or the
readonly setting converges automatically. Whether the guest can stay
running depends on the change.
**** Bind mode: readonly flips apply live; source changes need a stopped guest
A readonly flip is remounted in place while the machine runs. A source
directory change cannot be applied live: libkrun pins the old host bind
for as long as the machine runs, so the run halts with an ACTION REQUIRED
message naming the machine; stop it and re-run, and the stale bind is
unmounted and re-bound from the new source before the machine starts. A
rename (the share name changes while the source and target stay)
converges the same way through the ledger-stale cleanup, with the same
stopped-machine rule. Stacked binds at a share subdirectory (left by an
interrupted remediation or by manual stacking) are detected and collapsed
on the next run while the machine is stopped, and verify requires exactly
one layer after a successful run.
**** Direct mode: the guest must be stopped for the volume re-creation
A source or readonly change removes and re-adds the volume, so the
stopped-machine rule for volume changes applies.
**** When remediation is refused
If the ledger cannot prove that an existing bind is playbook-owned, the
run halts and names every affected host and guest path. Re-run with
-e bind_mounts_force_remount=true to accept; forcing unmounts and
replaces the listed mounts. Forcing also requires a stopped machine for
the same libkrun reason. Every stack layer is individually
ownership-checked, so force on its own accepts only layers the playbook
can prove it created. One bind is proven without the ledger: a mount root
the kernel marks //deleted - its source directory was deleted while it
stayed mounted - is playbook-owned when the path minus the marker matches
the configured or recorded source, and remediates on a stopped machine
without force, so it never reaches this refusal.

A layer it cannot prove, such as one left behind by an earlier layout
or mounted by hand, is accepted when its path is named in
bind_mounts_force_allow_prefixes, an extra-vars value that defaults to
empty and holds one path or several separated by commas. Only layers at
or below a named path are accepted, and a layer that is not named stays
refused even when force is set.

#+BEGIN_SRC
ansible-playbook playbooks/bind-mounts/bind-mounts.yml -i inventory -K -e bind_mounts_force_remount=true -e bind_mounts_force_allow_prefixes=/home/you/share-old
#+END_SRC
** Configuration reference
The block below shows the shape of vars.yml; every path in it is a fictitious
example. Copy playbooks/bind-mounts/vars.yml.example to playbooks/bind-mounts/vars.yml and replace names, users, and
directories with your own.

#+BEGIN_SRC yaml
mode: bind
share_root: /home/you/share
share_target: /mnt/share
machines:
  - name: my-vm
    user: you
    uid: 1000
    gid: 1000
    profile_path: /home/you/.bash_profile
    max_volumes: 4
    mounts:
      - name: website
        src: /home/you/projects/website
        target: /home/you/projects/website
        readonly: false
        uid: 1000
        gid: 1000
#+END_SRC
*** mode selects bind or direct operation
*** share_root holds the per-mount subdirectories
It is required in both modes and must be an absolute path without whitespace.
The provenance ledger is not stored here; it lives in the playbook user's
state directory (see Ledger).
*** share_target is the guest path of the share root in bind mode
*** machines holds one entry per smolvm machine with unique names
**** user plus uid and gid select the account and created-dir ownership
**** profile_path defaults to the bash profile of user in the guest
**** max_volumes caps the volume slots per machine
The default is 4. Machines created from a packed .smolmachine archive fit 3,
and every extra device, such as published ports, costs one more slot; hand
attached volumes count against the cap just like playbook-managed ones.
**** mounts lists the shared directories
***** src is the host directory and must exist before the run
***** target is the absolute guest path, unique per machine
***** name is the share subdirectory name in bind mode
It defaults to the last path component of src. The same name and src pair on
several machines means those machines share the subdirectory.
***** readonly is optional in both modes
Direct mode appends :ro to the volume; bind mode remounts the bind read-only.
***** uid and gid override created-directory ownership
They default to the machine-level uid and gid.
** Tag reference
*** The default run
Validate, volume convergence for stopped machines, host binds, start,
install, guest binds, verify. Works whether the guests are running or
stopped; a running machine that needs volume changes halts the run with an
ACTION REQUIRED message naming the machine and the command to run.
*** mounts
Host binds and guest binds only. Refuses stopped machines, because guest
binds need a running guest. Does not change the volume set: a pending
volume change stops the run and names the default run or --tags attach.
*** install
Preflights the guest user and home directory, then refreshes the guest
script, the sudoers drop-in, and the profile hook. Needs running machines,
a root exec user, and the configured user with an existing home directory
inside the guest. Does not change the volume set.
*** start starts stopped machines and waits for exec readiness
Does not change the volume set: converge with the default run or --tags
attach first if a volume change is pending.
*** verify checks every mount read-only after the run
Does not change the volume set.
*** attach converges the volume set; machines must be stopped
The default run already converges stopped machines automatically, so attach
is only needed for explicit, step-by-step control. It is also the way to
converge after a partial run (mounts, install, verify, start), which never
changes the volume set.
*** stop syncs each guest and stops the machines
Tolerates machines that are already stopped.
*** teardown undoes everything the playbook created
Direct-mode volume removal requires stopped machines. Guest helper copies
are the exception: the run that used them removes them, and a shutdown
clears them with the guest's tmpfs /tmp.

attach, stop, and teardown are excluded from the default run; select them
explicitly with --tags. Only the default run and --tags attach converge a
machine's volume set (teardown removes the volumes the ledger records); the
partial tags refuse a pending volume change instead of applying it.
** Mode switching
*** 1 Stop the machines
#+BEGIN_SRC
ansible-playbook playbooks/bind-mounts/bind-mounts.yml -i inventory --tags stop
#+END_SRC
*** 2 Change the mode or the mount list
Edit mode and the machines list in vars.yml.
*** 3 Run the default playbook
#+BEGIN_SRC
ansible-playbook playbooks/bind-mounts/bind-mounts.yml -i inventory
#+END_SRC

The run converges the volume set on the stopped machines and starts them
again. Bind to direct: every mount becomes a volume, the share volume is
removed, and the guest-side login hook, sudoers rule, and installed script
are removed. Direct to bind: the share volume is attached and former mount
volumes are removed. Only volumes the ledger proves the playbook created
are ever removed. A volume the configuration does not want at a target it
names, and which the ledger cannot prove, halts the run with instructions
and the exact removal command while the ledger is usable. Hand-attached
volumes elsewhere, such as a persistent home directory, are untouched and
still count against max_volumes.

For step-by-step control you can still converge explicitly with --tags
attach after stopping, and start the machines with --tags start.
** Safety model
*** The provenance ledger records what each run observes
The ledger lives in the playbook user's state directory, outside the share,
and records volumes, host binds, guest binds, and installed artifacts per
machine. It records those artifacts by kind, not by path, so changed
installed_script_guest_path or sudoers_dropin_guest_path values leave a copy
at the old path behind and untracked; the removals act only on the paths the
current configuration names. The guest helper copies are not in the ledger at
all: they are staged under the configured helper directory and removed by the
run that
used them, and such a removal touches a file only when it carries the
helpers' ownership marker. Its volume record
names each source as the canonical host path, and is written again as soon
as a run applies a volume change, so a run that fails before the final
ledger write still describes the volumes that are
attached. A bind enters the ledger only as an observation: the host-bind
probe found the target bound from that source, this run created the bind, or
the guest mount helper reported the target bound from the share path. Each
such entry carries the observation behind it, and the tasks that remediate a
bind act only on entries that carry one, so an entry from an older run - or
one from a run that could not look - is not treated as proof. A stopped
machine proves nothing about guest binds: a guest bind does not survive a
stop, so a run that finds a machine stopped records no guest-bind facts for
it, while the host-side layer and the volumes stay observable. Entries that
are in the ledger and in the configuration are maintained; entries in the
ledger but no longer in the configuration are removed; anything else is
foreign and never touched, except a volume the configuration does not want at
a target it names, which is refused while the ledger is usable.
*** Foreign mounts are refused, never unmounted automatically
A target already mounted with different content than the configured source
fails the run with the found and expected device:inode identities printed,
together with the manual resolution path. A bind the ledger does not
evidence as observed is refused that way too, instead of being unmounted on
the ledger's word. A volume the configuration does
not want at a target it names, which the ledger cannot prove, is refused
the same way while the ledger is usable; -e bind_mounts_force_remount=true
accepts removing and replacing it, with the machine stopped.
*** Idempotency compares device and inode, not just mount presence
Every check compares the device and inode of the mounted target against the
configured source, so a stale or wrong-source mount is caught instead of
silently skipped. Source-path comparison is deliberately avoided because the
kernel reports bind sources in normalized form that cannot be matched by
string equality. The one exception is the kernel's //deleted mount-root
marker: the unlinked directory's inode can never be compared again, so
such a bind is recognized by its path with the marker stripped.
*** Volume changes fail on running machines instead of stopping them
The attach tag refuses running machines and prints the exact commands to run;
the playbook never stops a machine with live sessions on its own.
*** The sudoers rule is scoped to a root-owned script copy
The login hook runs sudo -n against the root-owned 0755 copy of the script.

#+BEGIN_SRC
<user> ALL=(root) NOPASSWD: /usr/local/sbin/bind-mount-on-guest.sh
#+END_SRC

The drop-in is validated with visudo before activation. It is installed at
sudoers_dropin_guest_path (default /etc/sudoers.d/010-bind-mounts), which
must stay in a directory the guest's sudoers includes. The rule authorizes
only the root-owned 0755 copy at installed_script_guest_path (default
/usr/local/sbin/bind-mount-on-guest.sh); keep that path in a root-owned
directory outside the share, because a script the guest user can replace
runs as root under NOPASSWD. Both are play variables, set with -e rather
than in vars.yml.
*** Writes are atomic and preserve ownership and mode
Ledger and profile edits go through a temp file and rename, and the volume
record a run writes after a volume change goes to the ledger the same way,
so a reader never sees a partial file. The profile helper preserves the
file owner and mode and never touches lines outside the managed block,
which uses the standard blockinfile markers.
*** Check mode skips every mutating task and still verifies
No volume change, mount, install, or stale-state removal runs. The
read-only checks do: the host-side probes, the host bind identity check,
and both guest verifications. The guest checks run the same read-only
work the mount phase stages, but inline through the machine's exec, so a
check-mode run writes nothing and leaves nothing in a guest. Check mode
asserts that the current state satisfies the contract; it does not
predict changes, so on a state that is not converged it stops with the
same refusals a real run raises: a pending volume change on a running
machine, an unknown machine state, a volume the ledger cannot prove, an
exceeded volume budget, a missing source, or a stopped machine whose
mounts are requested. A stopped machine is not guest-verified, because
the guest checks need a running machine.
** Shutdown semantics
smolvm machine stop is graceful: the guest agent runs a full sync, flushing
every filesystem including virtiofs, remounts the storage read-only to
checkpoint its journal, and only then is the VMM terminated, after which the
host fsyncs the disk files. Guest processes get no chance to clean up; it is
sync-then-kill, like pulling power after sync, so save editor buffers first.
The stop tag adds a redundant guest sync before stopping as belt-and-braces.
** Glossary
*** Bind mode
One share volume per machine; each configured directory is bind-mounted
into the share root on the host and from the share to its target path
inside the guest. A guest-side umount is skipped when the target carries a
volume: the guest cannot tell a volume mount from a bind, and the mount at
that target is smolvm's own.
*** Direct mode
Each configured directory is attached as its own smolvm volume, with no
share volume and no guest-side artifacts.
*** Device:inode identity
The pair of device and inode numbers reported by stat. Equal identity
means two paths reference the same content; this is how bind mounts are
verified, because bind sources cannot be compared as strings; the
kernel reports them in normalized form.
*** Exec user
The user as whom smolvm machine exec runs commands inside a guest.
Management operations require it to be root.
*** Foreign state
Any mount, volume, or file the ledger cannot prove the playbook created.
Ignored when nothing depends on it; refused when it sits where the
configuration wants a different mount or volume. Never removed unless
-e bind_mounts_force_remount=true accepts it.
*** Force remount
Replacing a bind, or an attached volume at a target the configuration
names, whose ownership the ledger cannot prove, authorized by re-running
with -e bind_mounts_force_remount=true; the refusal message lists every
affected mount and volume before anything is forced. A foreign guest-side
mount is not covered: the run prints the exact umount command instead.
*** Guest bind: a bind mount from the share path to the target path
*** Guest-side share path: share_target followed by the mount name
*** Host bind: a bind mount from a source directory to its share subdirectory
*** Ledger
The file .bind-mounts-state.yml in the playbook user's state directory,
~/.local/state/bind-mount-on-host-and-guest/, mode 0644. It records
everything the playbook created, is read at the start of a run, and is
written again by the playbook's own user, without sudo or become, whenever
a volume change is applied and at the end of a successful run; it is the
basis of provenance and stale-element cleanup. It sits outside the share
root, so no guest can see it.
*** Login hook
The managed block in the machine user's .bash_profile that re-applies
the guest binds at every login through passwordless sudo.
*** Mount entry: one host directory plus its guest target path in vars.yml
*** share_root: the host directory holding one subdirectory per mount entry
*** share_target: the guest path at which the share root is mounted
*** Share volume: the one smolvm volume backed by the share root
*** Stale element: ledger-proven state the configuration no longer lists
*** Volume: a host directory attached to a machine as its own virtiofs device
** Troubleshooting
*** A missing vars.yml fails fast with copy instructions
*** A target mounted with a different source is remediated or refused
A proven-stale bind is unmounted and re-bound from the configured source
while the machine is stopped; a running machine halts the run with an
ACTION REQUIRED message first (libkrun pins the old bind). A bind whose
source directory was deleted while it stayed mounted — the kernel marks
its mount root //deleted — is treated as ours when the path minus that
marker matches the configured or recorded source, and remediates on a
stopped machine without force. When the ledger
cannot prove the bind is ours, the run halts and lists every affected host
and guest path; re-run with -e bind_mounts_force_remount=true to accept, or
unmount manually. A volume the configuration does not want at a target it
names, which the ledger cannot prove, is refused the same way while the
ledger is usable; a guest mount whose target carries a volume is not
unmounted, and the run prints the volume and the host-side recovery
instead.
*** After a host reboot a standalone start mounts nothing
Host binds are runtime state and do not survive reboots, so the share
subdirectories are empty and the guest scripts refuse to bind from them.
Run the playbook: it re-creates the host binds and the guest mounts.
*** Refused volume changes mean stop, then re-run
The playbook never stops a machine with live sessions on its own. After
stopping, re-run the default playbook (no --tags): it applies the volume
changes, starts the machine, and finishes the rest. For step-by-step
control, run --tags attach first, then --tags start.
*** An exceeded volume budget counts hand-attached volumes too
Remove mounts from vars.yml, or raise max_volumes only if you know the
machine has headroom; see smolvm issue
[[https://github.com/smol-machines/smolvm/issues/941][#941]].
*** An unreadable ledger disables cleanup for that run
Fix or delete
~/.local/state/bind-mount-on-host-and-guest/.bind-mounts-state.yml; the
playbook user owns it, so no sudo is needed. Deleting it loses the cleanup
bookkeeping, and with no proof at all a volume the configuration does not
want at a target it names is left alone instead of refused. While the file
exists and is unreadable nothing is written either, so fix or delete it,
then re-run to record the volumes a run changes. With the file gone, a run
that applies a volume change writes the volume facts it recorded. A
.bind-mounts-state.yml left in the share root by an older version is
ignored; delete or move it.
*** The smolvm exec user must be root for the playbook to manage a guest
**** Context
The playbook reaches a guest only through smolvm machine exec, which runs
as the exec user configured on the machine. Installing the login hook
writes root-owned files (the script at the configured script path and the
sudoers drop-in), and the guest-side mounts need root.
**** Cause
The machine's configured exec user is not root, typically because it was
created with a non-root --user default; the playbook fails the run
with the machine's uid in the message.
**** Solution
Create or update the machine without a non-root --user default, then
re-run the playbook.
*** The guest user or home directory is missing
**** Context
Installing the login hook needs the machine's configured user to exist
inside the guest, with a home directory for the managed .bash_profile
block.
**** Cause
The machine was created without the user (or without a home directory
for it), so the preflight finds neither and refuses to continue.
**** Solution
Create the user and home directory inside the guest, e.g.: smolvm
machine exec --name <machine-name> -- sh -c "useradd -m -u <uid>
<user>" (adjust to your guest's user tooling), or set profile_path in
vars.yml to an existing directory, then re-run the playbook.
